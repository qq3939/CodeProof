# M1 仓库分析

## 1. 本阶段做了什么

实现了"提交仓库 → 分析出画像和考点"的完整流水线：规范化 GitHub 地址，`git ls-remote` 解析出提交 SHA，靠唯一约束保证同一提交只分析一次；worker 浅克隆（禁用 hooks、限制大小和文件数、超时），用 tree-sitter 解析所有 Java 文件得到符号和调用，近似解析调用关系，提取 Spring 画像（技术栈、配置项、接口、组件、事务/缓存/Redis/消息/定时/异步/并发用法、调用链），再从画像里挑候选考点交给快模型写成考点。进度通过 Redis 发布订阅 + SSE 推给页面；仓库页可以看画像、文件树和高亮的代码。

## 4. 面试可能怎么问

1. **同一个仓库被两个人同时提交，怎么保证只分析一次？** 原理：数据库唯一约束是并发下最可靠的去重手段。→ 本项目：`UNIQUE(repository_id, commit_sha)` + `ON CONFLICT DO NOTHING RETURNING`，拿到 id 的请求才投递任务（D-001）。→ 局限：快照建了但任务投递失败，会留下一个永远排队的快照，需要运维页重试。
2. **为什么不直接编译项目拿到准确的调用关系？** 原理：编译需要下载依赖、执行构建脚本，等于运行不可信代码。→ 本项目：tree-sitter 只做语法分析，近似解析调用（D-002）。→ 局限：链式调用、Lambda、重载会解析失败；画像里给出解析率。
3. **克隆不可信仓库有哪些风险？怎么防？** 原理：git hooks、超大仓库、符号链接指向系统文件、LFS 拉取大文件。→ 本项目：禁用 hooks、浅克隆、大小和文件数上限、超时；沙箱拒绝跟随指向仓库外的符号链接。→ 局限：git 本身的漏洞防不住，所以 worker 用非 root 用户运行。
4. **SSE 和 WebSocket 的区别？为什么进度用 SSE？** 原理：SSE 是基于 HTTP 的单向推送，自动重连；WebSocket 是双向的。→ 本项目：进度只需要服务端推，SSE 足够；连接建立时先推一次当前状态，刷新页面也能看到。→ 局限：HTTP/1.1 下每个域名同时最多 6 个连接。
5. **多个 api 进程时，怎么把 worker 的进度推给连在任意一个 api 上的浏览器？** 原理：发布订阅。→ 本项目：worker 往 Redis 频道 `job:{id}` 发布，每个 SSE 连接各自订阅。→ 局限：Redis 发布订阅不持久，订阅之前发的消息会丢，所以连接时先读一次数据库里的当前状态。
6. **候选考点为什么要按类型限额？** → 本项目：真实仓库里事务、缓存注解特别多，不限额考点会被一种类型占满（P-006、D-011）。
7. **配置文件里有密码怎么办？** → 画像只保留配置键，值一律 `***`；沙箱拒绝读取 `.env`、私钥等敏感文件；评测里有专门的泄露检查。

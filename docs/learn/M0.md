# M0 骨架

## 1. 本阶段做了什么

搭好了整个项目的地基：FastAPI 后端（配置、JSON 日志、统一错误格式、健康检查、请求 ID、CSRF 来源校验、限流），SQLAlchemy 2 异步 + Alembic 迁移（含 pgvector 扩展和 HNSW 索引），arq 后台任务和自建 `jobs` 表，GitHub OAuth 登录 + 开发登录 + `/me`，可替换的模型客户端和假模型，Vue 3 前端骨架，Docker Compose 五个服务（都带健康检查），以及 CI。

## 4. 面试可能怎么问

1. **为什么登录凭证放 HttpOnly Cookie，而不是 localStorage？**
   原理：localStorage 能被页面上任何 JS 读取，一旦有 XSS 就会被偷走；HttpOnly Cookie 浏览器会自动带上，但 JS 读不到。→ 本项目：JWT 放在 `pb_session` Cookie，配合 SameSite=Lax 和 Origin 校验防 CSRF；MCP 客户端没有浏览器，用另外的个人令牌。→ 局限：Cookie 方案要自己防 CSRF；JWT 无法提前作废，只能等过期（7 天）。
2. **OAuth 里的 state 参数是干什么的？**
   原理：防止攻击者把自己的授权码塞给受害者（登录 CSRF）。→ 本项目：登录前生成随机 state 存进短期 Cookie，回调时比对。→ 局限：state Cookie 只有 10 分钟有效期，用户在授权页停留太久会登录失败。
3. **为什么要有后台任务队列？为什么选 arq？**
   原理：HTTP 请求应该快速返回，耗时任务异步执行，失败可重试、可观测。→ 本项目：分析仓库要几十秒到几分钟，阅卷要调多次模型，都在 worker 里跑；arq 是 asyncio 原生的，和 FastAPI 共用同一套异步代码。→ 局限：arq 功能比 Celery 少（没有任务编排、优先级）；所以自建了 jobs 表补上可观测性。
4. **Compose 里 depends_on 和 healthcheck 怎么配合？**
   原理：`depends_on` 只保证启动顺序，加上 `condition: service_healthy` 才会等依赖真正可用。→ 本项目：api/worker 等 migrate 成功结束，migrate 等 Postgres 和 Redis 健康，前端等 api 健康。→ 局限：健康检查只说明"进程活着、能连数据库"，不代表业务功能正常。
5. **为什么测试不用真实的模型 API？**
   原理：测试要可重复、离线、不花钱，真实模型输出不确定。→ 本项目：假模型按任务名分发，根据输入计算结果，能区分好回答和差回答（见 D-013）。→ 局限：测试通过不代表真实模型效果好，需要单独的评测（M6）。
6. **数据库迁移为什么单独做一个服务？**
   原理：多个进程同时执行迁移可能冲突。→ 本项目：`migrate` 服务只跑一次 `alembic upgrade head`，api 和 worker 等它成功后再启动。→ 局限：迁移失败时整个系统起不来，需要看 migrate 的日志。
7. **限流是怎么做的？有什么缺点？**
   见 D-009：Redis 固定窗口，窗口边界最多放过 2 倍请求；Redis 挂掉时放行。
